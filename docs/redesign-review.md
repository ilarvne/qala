# Focused redesign integration review

Initial source review on 2026-10-19, followed by the focused fixes and browser verification recorded below. The initial review was read-only; no broad test suite was rerun by this reviewer. Line references in the findings describe the original reviewed snapshot and may move during fixes. This document does not claim visual approval, an actual walk, real-device GPS verification, or a provider phone call.

1. **P1 — Bootstrap can overwrite a newer user plan.** In `src/hooks/usePlanner.ts:78–86`, the initial memory lookup is followed unconditionally by `plan(initialQuery, initialSettings, false)`. If a user changes location/time or submits a request while that lookup is pending, bootstrap can abort the newer planner request and later install a result for the original settings. The controls retain the user's settings. Guard bootstrap with a request/context revision or start it before allowing a newer request to supersede it; every result commit should verify its current context.

2. **P1 — A GPS error can leave an untracked location watcher running.** `src/App.tsx:160–164` sets `following` false but does not clear `watchRef`. A `watchPosition` timeout can be followed by later successful position callbacks. Retrying then overwrites the stored watch ID (`:190–194`), so ending navigation cannot clear the first watcher. Clear/reset the active watcher when a watch fails before advertising that updates have stopped. Check timeout → retry → end navigation and confirm each created watcher is cleared.

3. **P1 — The old itinerary remains startable under new constraints.** `src/App.tsx:66–70` reads the available budget from the previous result, while `usePlanner.update()` changes controls and leaves that result visible during the refresh. The Start button (`src/App.tsx:316`) is disabled only for street routing. Changing 90 to 30 minutes and immediately starting can therefore launch the previous longer itinerary against its previous budget. Invalidate navigation when planning context changes, and prevent every navigation entry point from starting a result that is pending replacement.

4. **P2 — The instruction list bypasses the over-budget gate.** The primary start actions check or disable on `overBudget`, but every button under “All walking instructions” (`src/App.tsx:367`) calls `setNavigating(true)` without that check. Apply the same budget/current-context guard to these buttons. Previewing an instruction should not start a blocked itinerary.

5. **P2 — Provider entrance-offset warnings are discarded.** `backend/navigation.py:178–207` returns snapped waypoints and warnings when a requested place is more than 75 m from the mapped path. `StreetRoute` (`src/components/CityMap.tsx:8–27`) omits these fields and the route caveats (`src/App.tsx:370–372`) show only planner warnings and a generic sentence. Preserve and render the router's warnings, preferably beside the affected stop, so a materially displaced endpoint is visible before walking.

6. **P2 — Live progression cannot recover after passing the next turn.** `src/App.tsx:132–138` advances only when a fix is within 25 m of the single next maneuver. Enabling GPS after the first turn, or passing that radius between fixes, leaves the display stuck on an earlier step. The backend supplies `geometry_start_index`/`geometry_end_index` (`backend/navigation.py:172–173`) but the frontend drops them. Use bounded forward progress along the route geometry, retain manual correction, and verify a mid-route start plus a skipped GPS fix before claiming robust automatic turn progression.

7. **P2 — The language selector no longer covers the redesigned interface.** AgentPanel and map strings localize, but almost all new App controls, route directions chrome, privacy text, evidence dialog and PlaceCard labels are hardcoded English (`src/App.tsx:324–383`, `src/components/PlaceCard.tsx:24–35`). Selecting RU/KZ updates `document.lang` without translating those actions. Restore the existing localized-copy path for the shipped controls and their accessible labels. Kazakh provider instructions can remain explicitly identified as English fallback.

The original reviewed adapter already rejected aborted responses and passed a request-context snapshot to `acceptResult`; the hook compared that snapshot with current context. Backend routing also validated pedestrian mode, shape bounds, leg count, narrative language and summary consistency. The fixes below add the separate bootstrap, navigation-start and watcher-cleanup protections.

## Fix status

- Finding 1: fixed with an interaction revision guard and bootstrap suppression after user actions. Browser verification held the actual memory response, changed duration rapidly to 90 then 45, and confirmed that only those two real recommendation requests occurred. The final controls and stops matched the 45-minute response.
- Finding 2: fixed with `clearWatch` and watch-ID reset on geolocation error. Synthetic browser callbacks verified timeout → retry → end navigation: watcher IDs 100 and 101 were each cleared and no watcher remained active. This verifies ownership and UI behavior, not device location accuracy.
- Finding 3: fixed with planning-context fingerprints and shared start guards. Browser verification confirmed primary start, route start and every instruction were disabled during a held replacement response and remained disabled after an injected browser transport failure. The held response came from the real API; its body was not fabricated.
- Finding 4: every instruction now uses the shared `canStart` guard, including `!overBudget`. Browser checks exercised the pending/failed-context branches for that same list. No naturally over-budget street route was encountered in this bounded run, so that specific browser branch remains unexercised.
- Finding 5: router warnings now render before start controls. Verified with the actual Kazakh fallback warning returned by the routing endpoint. The initial real route had no snap warning, so a displaced-entrance case was not manufactured or claimed as tested.
- Finding 6: `src/lib/navigation-progress.ts` is implemented and wired into the navigation UI. All 12 executable probes in `scripts/check_navigation_progress.mjs` pass, covering a mid-route start, skipped turns, poor accuracy, off-route fixes, backward jitter, a crossing and duplicate leg boundaries. A focused strict TypeScript check passes. Browser verification injected a fix on the real returned geometry, advanced from the first instruction to step 11 of 13, and confirmed a backward fix did not reverse it. Actual-device walking verification remains separate.
- Finding 7: remains a known limitation. The assistant/map localize, while several redesigned controls, route chrome, evidence text and accessible labels remain English. This review did not expand the current functional-fix scope to rewrite those strings.
